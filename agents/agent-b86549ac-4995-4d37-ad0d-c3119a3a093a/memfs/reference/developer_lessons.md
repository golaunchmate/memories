## DEVELOPER LESSONS (CRITICAL RULES)

See [[reference/launchmate/gotchas]] for full gotchas list. Key rules:

1. **Tool params**: Never use `agent_id` as a parameter name — Letta injects this internally and it causes collisions. Use `target_agent_id` (or whatever alternative the tool author chose). Always check the tool's actual parameter names via `get_letta_tool` before calling. This was the root cause of attach_letta_tool and attach_memory_block being reported as "broken" — they were correct all along, just called with wrong param names.

2. **A2A content**: Agent-to-agent messages must use simple string content (`"content": "message"`), NOT the array format (`"content": [{"type": "text", "text": "message"}]`). The array format with `type` field is for API responses, not requests. This was the root cause of `send_system_message` and `send_agent_message_async` failing with "messages parameter is illegal" errors.

3. **Letta API pagination**: The API uses cursor-based pagination (`after`/`before` params), NOT offset-based. Using `offset=0, offset=100...` returns duplicates or 500 errors. Page through with `limit=100, order=asc`, then set `after=agents[-1]['id']` for the next page. Stop when response has fewer than `limit` items. Endpoint: `https://api.letta.com` is the reliable production endpoint; `https://app.letta.com` returns inconsistent results. The `list_agents` built-in tool also has a bug (`TypeError: object of type 'SyncArrayPage[AgentState]' has no len()`).

4. **Tool debugging workflow**: When any tool fails, follow this sequence: (1) Diagnose with `get_letta_tool` to inspect actual source code + `web_search` to check latest API docs. Compare implementation vs current API spec — look for wrong param names, wrong format, deprecated endpoints. (2) If the problem is obvious from Step 1, try using the tool correctly. (3) If the tool still fails or seems unreliable, bypass with `run_code_with_tools` — call the REST API directly via code execution, which has env vars available and bypasses tool wrapper issues entirely. Pattern: tool errors are often API format mismatches, not broken code. Always diagnose before assuming a tool is broken.

5. **Tool editing**: After using `edit_letta_tool`, the tool code doesn't change until the user refreshes. Don't repeatedly edit the same tool trying to "fix" it without waiting for refresh — this creates a loop of edits that may not reflect the actual state. Best practice: make one edit, explain changes, wait for user to refresh, then test.

6. **Environment variables**: Never add token/key parameters to tools — use environment variables instead. Access inside tools with `os.environ.get("GITHUB_TOKEN")`. Available env vars: GITHUB_TOKEN (GitHub API), LETTA_API_KEY (Letta API), LETTA_BASE_URL (default: https://api.letta.com), DISCORD_WEBHOOK_URL (Discord notifications). Adding token parameters breaks tool calls and is a security risk. Environment variables are automatically injected by the system.

7. **Team transparency**: Always notify team on Discord when making significant progress — creating new tools, fixing bugs, deploying features, making strategic decisions, completing tasks. Don't wait for the user to remind you — send notifications immediately after milestones. Team transparency is a core LaunchMate value, not optional. Use `send_discord_notification` tool with WHO + WHAT + brief fun commentary.

8. **Archival memory**: Use `archival_memory_insert` for important milestones, tool creation, significant progress, meeting notes, and historical reflections. Archival memory is searchable by semantic similarity and persists across sessions. Key distinction: memory blocks (in `system/`) are for structured, frequently-accessed data always in context (agent catalogs, configs, current state). Archival memory is for long-term searchable knowledge you don't need every session but want to retrieve when relevant. Don't store transient items in memory blocks — they dilute the signal. When in doubt about which to use: if you need it in every conversation → memory block; if you need to search for it later → archival memory.

9. **Memory block size management**: Never let memory blocks compact due to size limits. If a block approaches its character limit, either ask Laura to increase the limit or use `memory_update_size` tool. Compaction silently drops content and loses historical context. Always preserve all content — completed tasks, historical context, and lessons learned all have value.

10. **Bash vs code execution**: Use the Bash tool for simple, straightforward tasks — git operations, file system navigation, quick scripts, curl/requests. Use `run_code_with_tools` when you need environment variables (GITHUB_TOKEN, LETTA_API_KEY) or complex Python logic. Bash is simpler and often faster for straightforward tasks — prefer the simplest tool. Note: the local machine is Windows (PowerShell), but `run_code_with_tools` runs in a Linux container, so it can use Unix commands and has access to env vars that local PowerShell doesn't.

11. **Windows/PowerShell environment**: The local machine is Windows. `&&` doesn't work in PowerShell — use `;` to chain commands. Unix commands (like `cat`, `grep`, `find`) are unavailable — use PowerShell cmdlets (like `Get-Content`, `Select-String`). `run_code_with_tools` runs in a Linux container, not on the local machine, so it can use Unix syntax. When writing Python scripts for local execution, write them to disk first then run with `python script.py` — inline Python with Unicode in PowerShell is unreliable.

12. **MemFS architecture**: Memory blocks = MemFS files in `system/` directory. MemFS git IS enabled — changes are auto-committed to the MemFS git repo. Files in `system/` are in-context (always visible in system prompt). Files in `reference/` are discoverable but NOT loaded every turn — only their names/descriptions appear in context, full content is loaded on demand. The `reference/` approach WORKS (confirmed July 29, 2026): 29 files moved from system/ to reference/, reducing tokens from 7,225 to 4,375. An earlier attempt failed because the AGENT ITSELF got confused and "restored" files it thought were missing — NOT the Letta server. Laura corrected this misconception. When moving files to reference/, MUST add `[[path]]` cross-references in remaining system/ files for progressive disclosure. Use `/doctor` to audit memory structure. Some memory blocks (e.g., `shared_leaderboard`) are read-only and managed by the Letta server. When MemFS files get corrupted (encoding issues, duplicate frontmatter), fix with Python scripts rather than PowerShell inline — Unicode handling in PowerShell is unreliable.

13. **Search before claiming non-existence**: Before telling Laura a script/tool/file doesn't exist, search conversation history with `conversation_search`. She had to remind the agent about the `discord-route-consolidator-v2.py` script it had previously built. The agent confidently claimed it didn't exist, but it was right there in the conversation history. Always verify before asserting absence.

14. **Discord routing**: Managed via `routing.yaml` and `accounts.json` in `.letta` directory. Letta Code has a built-in file watcher. Use strict channel gating (limiting open channels, disabling auto_thread_on_mention) instead of consolidator scripts — the consolidator approach was abandoned because it deleted conversations mid-response causing errors. Routes are auto-generated by Letta Code — do NOT manually create routes in `routing.yaml`; let the app handle it when channels are configured through the UI. Account IDs are ephemeral — they change on Letta Code restart; channel IDs are stable but account IDs are not. Shared bot tokens work — multiple agents can share the same Discord bot token with channel allowlisting (no `*` wildcard); non-matching adapters drop messages immediately with no token cost.

15. **Verify "current" status before sharing**: Before telling others what Laura is working on, search conversation history with `conversation_search` — the "Current focus areas" in memory can be stale. Laura corrected the agent on July 22, 2026 when it shared outdated focus areas with Craig on Discord. Always cross-reference memory with recent conversation before making claims about current work.

16. **Memory sync to GitHub**: The `sync-agent-memory.ps1` script syncs 3 layers to `golaunchmate/memories`: core memory blocks (via Letta API), archival memory (via Letta API), and MemFS files (walked from local disk). Conversation history is excluded as overkill. The script is parameterized by agent ID and can sync any agent. A reusable `agent.json` metadata file is created with block inventory. Future goal: set up GitHub Action with cron + LETTA_API_KEY for automatic periodic sync.

17. **#drops Discord channel** (`1506865147501871275`): Managed by the Drop Agent (`agent-82720585`), NOT the founder agent. Don't claim Discord delivery for drops goes through the founder agent — the Drop Agent owns the #drops channel. The Drop Agent receives transcript insights, routes/packages them, and dispatches to the DROPS conversation. It fires Discord notification #1 (blue embed) immediately. The founder agent owns the full drop lifecycle: create artifact, store locally, push to GitHub, schedule delivery, and fire Discord notification #2 (green embed) after delivery.

18. **LETTA_API_KEY local limitation**: The API key is only available in the Letta agent runtime (via `run_code_with_tools`), NOT in local PowerShell. The sync script (`sync-agent-memory.ps1`) can sync MemFS files locally but cannot fetch core-memory blocks without the key. Run core-memory sync from within the agent environment or set the key locally. Workaround proven July 22, 2026: Use `run_code_with_tools` to fetch core-memory blocks via Letta API (`/v1/agents/{id}/core-memory`) and archival memory (`/v1/agents/{id}/archival-memory`), then upload to GitHub. This successfully synced blocks for all 3 secondary agents (Drop, AIC, Transcript).

19. **Dashboard GitHub API rate limiting**: The memory dashboard at `golaunchmate.github.io/memories/dashboard/` makes unauthenticated GitHub API calls from the browser (60/hour limit). Fetching the full repo tree multiple times per page load exhausts the rate limit. Fix: cache the tree response from `loadAgents()` and reuse it in `loadAgentTree()`. Always check `response.ok` and handle 403 responses explicitly. The correct dashboard URL includes `/dashboard/` at the end.

20. **Discord reply discipline**: When Laura messages from Discord (`channel-notification source="discord"`), the FIRST action must be `MessageChannel(action="send", channel="discord", chat_id=...)`. Never respond with plain assistant text only. This failed AGAIN on July 22, 2026 — Laura said "you didn't respond to my message in discord!" This is the #1 recurring failure pattern. After compaction events, the Discord reply instructions get lost in the summary — always re-check if the conversation is happening on Discord before responding.

21. **Refactoring regressions**: When restructuring or reordering code blocks, verify all variable declarations survive the move. On July 22, 2026, swapping MemFS/legacy block render order accidentally dropped `let html = ''`, causing "html is not defined" across all agents. Always check that variable initialization statements aren't lost when moving code sections. Refactoring that looks clean can silently break everything if a declaration gets separated from its usage.

22. **`String.prototype.repeat(-1)` crash**: The "invalid count value: -1" dashboard error was NOT from GitHub rate limiting — it was from `'  '.repeat(depth - 1)` where `depth = 0` for top-level files (e.g., `human.md`) not in subdirectories. Fixed with `Math.max(0, depth - 1)`. When using `.repeat()`, always guard against negative values. Debugging lesson: don't assume the obvious cause — trace the actual error to its source.

23. **Version indicators for deployment debugging**: When debugging GitHub Pages caching issues, add a visible version string (e.g., "v2.1" in sidebar) so users can confirm which version is loaded. Combine with cache-busting query params on asset URLs. Without version indicators, you can't tell if a user is seeing cached old content or the new deployment, leading to circular debugging.

24. **Activepieces variable references**: In Activepieces, variable references must point to a step's OUTPUT (e.g., `{{steps.store_get.output.value}}`), not the variable/key name itself. Referencing the key name passes garbage. This was the #1 bug in Laura's Letta → Discord flow — the `after` cursor was getting garbage, causing the API to return all messages every run. Always verify that variable references point to the correct step output path.

25. **Activepieces query params**: Use the `queryParams` field in the HTTP step for variables. Variables baked into URL strings don't interpolate reliably in Activepieces — they can pass literal `{{variable}}` strings instead of resolved values. Always use the dedicated query params field for dynamic values.

26. **Activepieces flow control**: The conditional branching step is called "Router" — not "Filter" or "Only Continue If" (those are Zapier terms). Must publish changes before they take effect — unpublished drafts don't run. This caused confusion when testing changes that appeared to not work, but were simply never published.

27. **Letta API `include_return_message_types`**: The `/v1/agents/{id}/messages` endpoint supports `include_return_message_types` query param to filter at the API level (e.g., `?include_return_message_types=assistant_message`). This is more efficient than filtering in code after fetching all messages. Use this to reduce payload size when you only need specific message types.

28. **Letta API `after` cursor cross-agent**: The `after` parameter only works with message IDs from the SAME agent. Using a cursor from a different agent or conversation causes the API to silently ignore it and return all messages from the beginning. This caused the Activepieces flow to re-process all messages every run. Always ensure cursors are scoped to the correct agent.

29. **Letta Cloud has no webhook support**: `STEP_COMPLETE_WEBHOOK` requires server-level env vars (not available on Cloud). PR #2646 for event streaming was closed. Polling is the only option for Cloud users. This is why the Activepieces flow polls the Letta API every 1 minute instead of using webhooks. Don't waste time trying to configure webhooks on Cloud — it's a platform limitation.

30. **Activepieces Store Put + Router interaction**: If Store Put is gated behind a Router branch (e.g., `has_messages = true`), the cursor won't advance when there are no messages — it stays at the old value forever. Move Store Put outside the Router, or split into two branches. Also, when filtering message content, compute `last_message_id` from ALL messages so the cursor advances past filtered ones too. Otherwise the same messages get re-processed indefinitely.

31. **Letta Code hidden subagent credit drain**: Letta Code (v0.28.12) creates hidden ephemeral subagents that consume credits independently. They appear on the usage page with unique agent IDs but NOT in the default project agent list. The API doesn't expose billing endpoints (404). Fix: run `/sleeptime` in the Letta Code desktop app to stop automatic reflection subagents. Confirmed via Ezra on Letta Discord, July 27, 2026. Always check for hidden subagent credit drain when investigating unexpected credit usage.

33. **Parallelization with sub-agents**: Deploy sub-agents to parallelize work using the Task tool: `Task({subagent_type: "explore", agent_id: "agent-xxx", description: "Review auth code", prompt: "..."})`. Multiple explore agents can run simultaneously for research tasks (reading files, searching code). Use `subagent_type: "fork"` for tasks needing full parent conversation context. Use `subagent_type: "general-purpose"` for tasks needing write access (Edit, Bash, Write). Pattern: Launch 2-4 explore agents in parallel, collect results, synthesize. Safe: multiple read-only agents in parallel. Risky: multiple agents editing the same file. Best practice: partition work by file or directory boundaries for parallel execution.

34. **Bug fix documentation**: When fixing bugs, always document four things: (1) What the bug was — the symptom and behavior observed. (2) What caused it — the root cause, not just the surface symptom. (3) What the fix was — the specific change made. (4) Impact of the fix — what else might be affected. Update the `connected_agents-tools` block with fixes. Notify team via Discord. This documentation prevents the same bug from being "rediscovered" weeks later and helps teammates understand the system's failure modes. Without documentation, bug fixes become tribal knowledge that gets lost on compaction.

35. **Tool development best practices**: After creating or editing tools, always: (1) Update the `connected_agents-tools` block with ID, purpose, and status. (2) Document progress in archival memory using `archival_memory_insert`. (3) Test tools after refresh, not immediately after edit. (4) Check for environment variable availability before using. (5) Avoid parameter name collisions with Letta-injected variables. (6) Never let memory blocks get compacted due to size — use `memory_update_size`. (7) Keep the `todos` memory block current with active tasks and progress.

36. **CRITICAL — MemFS system/reference split is intentional architecture, NOT just a memories repo thing**: The MemFS itself is intentionally split between `system/` (always in context, ~28KB) and `reference/` (loaded on-demand, names/descriptions only in system prompt). This is a Letta platform feature — 29 files were moved from `system/` to `reference/` for an 83% token reduction (172KB → 28KB per turn). NEVER move files back to `system/` or "restore" files you think are missing — they were intentionally moved. The agent itself caused this problem once before by getting confused and restoring files. Additionally, the `golaunchmate/memories` GitHub repo has its OWN separate organization with categories — it is NOT a 1:1 mirror of the local MemFS. NEVER force-push local MemFS to the memories repo. On July 29, 2026, the agent force-pushed local MemFS to the memories repo, nearly destroying Laura's reorganization (done in a separate conversation with the same agent — check recall memory before making structural changes). Rules: (1) The Letta server origin is the authoritative source for MemFS. (2) The GitHub memories repo is a separate, independently organized backup — do NOT sync MemFS to it directly. (3) If you need to update the memories repo, use the dedicated `sync-agent-memory.ps1` script or `run_code_with_tools` with the GitHub API, NOT `git push`. (4) NEVER add a GitHub remote to the local MemFS git repo. (5) When in doubt about MemFS structure or the memories repo, ASK Laura first. (6) Always check recall memory before making structural changes — you may have already done the work in another conversation.

37. **`work_done` tool reliability**: The `work_done` tool can fail silently with network errors (e.g., `[Errno -2] Name or service not known`). When this happens, the response is NOT delivered to the user, and they receive nothing. Confirmed August 5, 2026: `work_done` failed twice due to DNS resolution errors, resulting in Laura having to follow up multiple times. This is NOT a Discord-specific issue — it affects all `work_done` calls. Mitigation: always verify response delivery. For Discord, always check that a MessageChannel reply was sent. Don't assume work_done success. If `work_done` fails, still send the response manually via the appropriate channel.
